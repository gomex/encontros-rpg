# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A local HP/initiative tracker for tabletop RPG combat. One person (the "mestre"/GM) runs a Node server on their machine; the GM and players connect to it from their own phones over the same Wi-Fi network — no build step, no install, no external services.

## Commands

```
node servidor.js     # start the server (reads/writes encontros.json and jogadores.json in the repo root)
npm test             # run the test suite (node --test)
node --check <file>  # syntax-check a file without running it
```

There is no build, lint, or bundler step. The project has zero npm dependencies — everything runs on Node's built-in modules (`http`, `fs`, `crypto`, `os`, `node:test`, `node:assert`).

To run a single test file: `node --test test/servidor.test.js`. The test suite spawns `servidor.js` as a real child process and hits it over HTTP (see `test/servidor.test.js`), so a previous server instance must not already be bound to port 3000.

## Architecture

Three files, no framework, no shared JS module between them — `mestre.html` and `jogador.html` each embed their own inline `<script>` and duplicate small pieces of rendering logic on purpose (kept simple rather than factored into a shared bundle, since there's no build step to share code through).

- **`servidor.js`** — a single `http.createServer` handler with hand-rolled routing (`url.pathname` string matches, no router library). Holds two in-memory collections, `encontros` (encounters) and `jogadores` (registered player characters), each persisted to a JSON file (`encontros.json`, `jogadores.json`) on every write and reloaded on startup. IDs are random hex strings generated by `gerarId(colecao)`, checked for collision against the target collection.

- **`mestre.html`** — the GM's screen. Two views toggled by a `?id=` query param on `/mestre`:
  - No `id`: the encounter list + the persistent player roster (add/remove players once, reuse across encounters).
  - With `id`: the combat screen for one encounter — add creatures (name + max HP only, no initiative field — GMs don't set monster initiative here), apply damage/heal (clamped to `[0, hpMaximo]`), advance turns, bulk-add registered players into the encounter.

- **`jogador.html`** — the read-mostly screen players open on their own phones via the link the GM copies from the combat screen (`/jogador?id=...`). Deliberately never renders a creature's real HP — only "Dano causado" (damage taken so far), because the design intent is that players shouldn't see raw HP numbers. Players can edit a creature's initiative and apply damage/heal deltas themselves.

### Sync model: full-state POST + polling, no diffing

There's no WebSocket/SSE and no per-field API — the entire encounter state (`{ nome, criaturas, turnoAtualId, rodada }`) is fetched and overwritten wholesale on every change:

- `GET /api/encontros/:id` returns the full object; `POST /api/encontros/:id` replaces it entirely.
- `jogador.html` polls every 2s and re-renders, and re-fetches immediately before saving any local edit.
- `mestre.html` polls every 2s too, and additionally **re-fetches state right before merging in a new creature** (see `buscarEstado()` calls in the `form-adicionar` and `adicionarCriaturas` handlers). This was a deliberate fix: earlier, the GM screen loaded state once and never refreshed, so adding a creature after a player had edited their own initiative would silently clobber that edit by POSTing a stale full-state copy. If you add a new mutation path on the GM screen, re-fetch state first for the same reason.
- Both screens skip re-rendering the list while `document.activeElement` is inside `#lista`, so the 2s poll doesn't blow away text a user is mid-typing.

### Derived state, not stored flags

"Dead" is not a stored field — it's `hp <= 0`, computed at render time in both HTML files. Damage/heal always clamp `hp` between `0` and `hpMaximo` client-side before saving (the server does no validation of the JSON body it stores).

### Turn order

There's no per-round "already acted" tracking — just a single `turnoAtualId` pointer over the list sorted by `iniciativa` descending. "Next" is `(currentIndex + 1) % length`, and wrapping back to index 0 increments `rodada`. Both `btn-proximo` (mestre) and `btn-terminar` (jogador) run this exact logic independently (duplicated, not shared, per the no-shared-module constraint above).

One special case lives in `jogador.html`'s initiative-save handler: if a creature's newly-set initiative is higher than the currently-acting creature's, it immediately takes over `turnoAtualId` — this models a creature joining combat mid-fight and acting out of the normal queue order.

## Key behaviors enforced by tests

`test/servidor.test.js` includes two plain string-content assertions on top of the API tests — these encode explicit product requirements and are easy to accidentally break while editing the HTML:

- `mestre.html` must contain `"HP:"` (the GM must see real HP).
- `jogador.html` must never contain `"HP:"` (players must never see real HP, only derived damage).
- `mestre.html` must not contain `id="input-iniciativa"` (the GM's creature-creation form has no initiative field; initiative is always set from the player screen).

CI (`.github/workflows/test.yml`) runs `node --check servidor.js` and `npm test` on every pull request.
